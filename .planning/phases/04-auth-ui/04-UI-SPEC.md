# Phase 4 — UI Design Contract

> Visual and interaction contract for the auth screens (`/login`, `/register`, `/forgot` stub), the reusable `<Field>` input, the `<AccountMenu>` Popover, and the typed mock auth seam at `lib/api/auth.ts`. Generated by gsd-ui-researcher.

This phase ships **form internals + a popover** on top of the AuthShell already shipped by Phase 3. It does NOT re-spec the AuthShell card geometry, the BrandMark, the page background gradient, or the centered-card disclaimer — those are owned by `app/(auth)/layout.tsx` (Phase 3) and remain unchanged. It does NOT introduce new design tokens — every utility referenced below already exists in `frontend/web/styles/globals.css @theme`. It does NOT ship the global auth context, `RequireAuth`, session rehydration, or `?from=` redirect — Phase 5 owns all of those (CONTEXT D-deferred).

If a needed token is missing this is surfaced as a blocker in §"Token Coverage Audit" rather than invented; the audit confirms zero blockers.

## Spacing Scale

Phase 4 consumes Tailwind's default spacing scale (4 px base unit). No new tokens. Reference numbers below come from `_design-reference/auth.jsx` (form geometry) and `styles.css:152-184` (input geometry).

| Token | Value | Usage in Phase 4 |
|-------|-------|------------------|
| 1 | 4px | (a) Inline gap between form-banner icon and message text; (b) `mt-1` micro-adjust between Terms checkbox row and the "Required" error when present (reference auth.jsx:147 `marginTop: -8` — Phase 4 omits the negative margin since the `gap-3.5` on the form already breathes correctly) |
| 1.5 | 6px | Field internal stack gap (`gap-1.5` between input and helper / error line — reference auth.jsx:43 `gap: 6`) |
| 2 | 8px | (a) Submit button icon gap (`gap-2` between "Sign in" / "Create account" label and the `ArrowRight` icon — matches `.btn` reference styles.css:110 `gap: 8`); (b) Form-banner internal vertical padding (`py-2` for the API-error banner — D-10) |

| `pl-3.5 pr-3` | 14px / 12px | `<Field>` input internal padding (`px-3.5 pt-[18px] pb-1.5`) — matches reference styles.css:157 `padding: 18px 14px 6px` (top 18 / right 14 / bottom 6 / left 14). Top padding `pt-[18px]` is a Tailwind arbitrary value because no scale step at 18 px exists; documented as a one-off, justified by the floating-label geometry. |

**Exceptions** (Tailwind arbitrary values used because no core scale step matches the reference exactly):
- `pt-[18px]` on the `<Field>` input — top inset for the floating label. Reference styles.css:157 uses `padding: 18px 14px 6px`; the 18 px top is the geometric anchor for the lifted-label position. No core scale step. Documented inline: `// non-tokenized: floating-label top inset 18px — see UI-SPEC §Spacing exceptions`.
- `top-[14px]` on the `<label>` (resting position) and `top-1.5` (= 6 px, lifted position) — reference styles.css:171 (`top: 14px`) and styles.css:179 (`top: 6px`). The 14 px resting top has no Tailwind core scale step; arbitrary value.
- `text-[10px]` on the lifted floating-label state — matches the eyebrow-style label visible when the input has content (reference styles.css:180 `font-size: 10px`). Below the Phase 2 type scale (`text-12` is the smallest token); intentionally arbitrary, mirrors the same Phase 3 escape hatch already documented for the mobile tab bar label.
- `tracking-[0.06em]` on the lifted floating-label state — matches reference styles.css:181 `letter-spacing: 0.06em`. Tailwind core has `tracking-wide` (= `0.025em`) and `tracking-wider` (= `0.05em`); neither matches the reference's specific 0.06em. Arbitrary value justified per-property because letter-spacing is not a token.

All four exceptions live inside `components/Field.tsx` only — they are an internal floating-label geometry, not reusable spacing decisions. No other file in this phase uses arbitrary values.

**Accent reserved for** (Phase 4 supplement to the Phase 3 list):
- Carried over from Phase 3 (unchanged): (1) active sidebar item indicator bar, (2) mobile primary CTA fill, (3) brand mark gradient, (4) brand mark middot.
- **NEW for Phase 4**: (5) Submit button fill (`bg-accent` / hover `bg-accent-hover`) on auth pages — this is the FIRST primary-CTA surface in the app since Phase 3 chrome had no CTA. (6) `<Field>` input focus-ring border (`focus:border-accent`) — matches reference styles.css:166 verbatim. (7) Terms checkbox `accent-color` (`accent-accent`) — matches reference auth.jsx:144. (8) Bottom-card link substring color (`text-accent` on `Create an account` / `Sign in`).
- **Off-limits** (Phase 4 will NOT use accent for): the popover (popover uses neutral surfaces — `bg-surface-elevated` / `bg-surface-2` only); the `Forgot password?` link (uses `text-text-secondary` per the reference, NOT `text-accent`); the form-level error banner (uses `text-danger` only, never `text-accent` even on the icon).

**Destructive reserved for** (NEW with Phase 4 — Phase 3 chrome had no destructive surfaces):
- (1) `<Field>` inline error text + border; (2) Form-level API-error banner; (3) Popover **Sign out** menu item label. **Nothing else.** Specifically NOT the `Forgot password?` link, NOT the bottom-card secondary copy, NOT the popover Account row.

**Form-level error banner color contract** (D-10):
- Background: `bg-danger/10` (Tailwind opacity utility on the danger token — produces ~`rgba(248,113,113,0.1)`). The opacity literal is a layout primitive, not a hex; permitted.
- Border: `border border-danger` (full-strength danger border).
- Text: `text-danger` (full-strength).
- Icon (lucide `AlertCircle`, 16 px): `text-danger`.
- Radius: `rounded-md` (= 10 px, Phase 2 token; matches the input radius for visual rhyme).

**Popover focus / hover treatment:**
- Trigger focus: browser default focus ring acceptable, OR explicit `focus-visible:outline-2 focus-visible:outline-accent focus-visible:outline-offset-2` to match the Phase 3 pattern on Sidebar items. **Phase 4 ships the explicit ring** — consistency with the Phase 3 chrome focus contract.
- Menu-item resting bg: `bg-transparent` (inherits popover content `bg-surface-elevated`).
- Menu-item hover bg: `bg-surface-2`.
- Menu-item focus ring: `focus-visible:outline-2 focus-visible:outline-accent focus-visible:outline-offset-[-2px]` — inset offset because the row sits inside the popover and an outset ring would clip against the popover border.
- Sign-out item hover: text stays `text-danger`, bg becomes `bg-danger/10` (matches the form-banner background tone — destructive surfaces use the same low-opacity wash for hover affordance).

## Responsive Behavior

Phase 4 inherits the chrome breakpoints from Phase 3 (`md` = 768 px). Within the AuthShell card, the form is **responsive only by virtue of fluid widths** — there is no breakpoint-specific layout rearrangement.

| Breakpoint | AuthShell card | Form width | `<Field>` width | Submit button width | Account popover behavior |
|------------|----------------|------------|-----------------|---------------------|--------------------------|
| `< 768px` (mobile, ~375 target) | Card width = `min(420px, 100% - 40px)` (Phase 3 contract); at 375 px viewport the card is 335 px wide with 20 px gutters. | 100% of card inner padding (`px-8` from layout = card content area is 356 px on a 420 px card; on a 375 px viewport, card is 335 px → content is 271 px). Form fields stack vertically with `gap-3.5`. | `w-full` (fills the form column). | `w-full` (full-width primary CTA, matches reference). | **N/A on auth pages** — `<AccountMenu>` lives on `Sidebar` and `Navbar` chrome; the auth route group does not render either. The popover is invisible to anyone on `/login` or `/register`. |
| `≥ 768px` (desktop, ~768 and 1440 targets) | Same card geometry — the AuthShell does NOT widen at desktop breakpoints (the centered card is intentionally 420 px max even at 1440 px, per reference). | 100% of card content area. | `w-full`. | `w-full`. | Anchored on Sidebar avatar (rail visible at md+) and Navbar greeting (when a logged-in user renders the home variant). The popover content opens **above** the trigger when there's not enough space below (Radix's default `side="bottom"` with `avoidCollisions` true), with `sideOffset={8}` for breathing room. Width: `min-w-44` (176 px) — fits both menu-item labels without wrapping. |

**Account popover positioning details (desktop only):**
- Sidebar avatar trigger (`w-9 h-9` circle at the bottom of the 64 px rail, near the viewport floor): popover should open to the **right** (`side="right"` on `<PopoverContent>`) since `side="top"` would clip into the rail and `side="bottom"` would clip below the viewport. `align="start"` so the popover top aligns with the avatar top edge.
- Navbar greeting trigger (right side of top bar at `py-6 px-10`): popover should open **below** (`side="bottom"`) with `align="end"` so the popover right edge aligns with the greeting right edge — keeps it within viewport bounds at all desktop widths.
- Both placements use `sideOffset={8}` (8 px buffer between trigger edge and popover edge).

**Z-index stack (Phase 4 additions):**
- Popover content: Radix manages portaling; the rendered element lives inside `<body>` at `z-50` (Radix default — above Phase 3's `z-30` chrome). No explicit `z-` utility passed — accept the Radix default.

**Transition behavior:**
- Popover open/close: Radix default Tailwind animations included by shadcn (`data-[state=open]:animate-in`, `data-[state=closed]:animate-out`, `fade-in-0`, `zoom-in-95`). These ship inside the shadcn-generated `popover.tsx` — accepted as-is.
- `<Field>` floating-label transition: `transition-all duration-150` matches the reference styles.css:175 `transition: all .15s ease`. Driven by Tailwind core utility, no custom keyframe.
- `<Field>` input border + bg transitions: `transition-colors duration-150` on the input — matches reference styles.css:164.
- Submit button hover: `transition-colors duration-150` (bg + bg-hover swap).

## Interaction Contracts

| Surface | Interaction | Behavior |
|---------|-------------|----------|
| `<Field>` input | Focus | Border becomes `border-accent`; bg becomes `bg-surface-elevated`; floating label lifts to `top-1.5` and shrinks to `text-[10px] uppercase tracking-[0.06em] text-text-secondary`. |
| `<Field>` input | Blur (with content) | Border returns to `border-border`; bg returns to `bg-surface`; label stays in lifted position because `:not(:placeholder-shown)` is true. |
| `<Field>` input | Blur (empty) | Border returns to `border-border`; bg returns to `bg-surface`; label drops to resting position (`top-[14px] text-[13px] text-text-muted`). |
| `<Field>` input | Type | Each keystroke calls `onChange(e.target.value)`. No debounce — validation runs only on submit, not per-keystroke. |
| `<Field>` show/hide eye toggle (password type) | Click | Toggles internal `show` state; changes input `type` between `'password'` and `'text'`; icon swaps `Eye` ↔ `EyeOff`. The toggle does NOT clear or modify the input value. |
| `<Field>` show/hide eye toggle | Focus | `focus-visible:outline-2 focus-visible:outline-accent focus-visible:outline-offset-2` (matches Phase 3 chrome focus ring). |
| `<Field>` show/hide eye toggle | Tab order | Receives focus immediately after the password input (it's a sibling `<button>` in the source order). |
| Auth form | Submit (Enter key in any field, or click on submit button) | Prevent default → run validator → setErrors object → if errors empty, call `signIn` / `signUp` → on success `router.push('/')` (D-11) → on `UsernameExistsException` set form-banner copy to `"An account with this email already exists."` → on `NotAuthorizedException` set form-banner copy to `"Incorrect email or password."` → on any other error (defensive) set banner to `"Incorrect email or password."` (collapse all unknown failures into the safe copy — never leak Cognito-internal messages). |
| Auth form | Submit while in flight | Re-submitting is no-op. The submit handler guards with `if (isSubmitting) return;` at the top. The submit button is also disabled via the HTML attribute, so Enter on a focused field that's not the button re-fires the form's `onSubmit` only if the form itself isn't disabled — the handler guard catches this. |
| Submit button | Click while disabled | No-op (HTML disabled). Cursor: `cursor-not-allowed`. |
| Submit button | Hover (resting) | Bg transitions from `bg-accent` to `bg-accent-hover` over 150 ms. |
| Submit button | Focus | `focus-visible:outline-2 focus-visible:outline-accent focus-visible:outline-offset-2` ring; ring color matches the button bg, but the offset gap (`outline-offset-2`) makes the ring visible against the dark page bg behind the card. |
| `Forgot password?` link (login page) | Click | `<Link href="/forgot">` — Next.js client-side navigation. The forgot stub renders inside the same AuthShell — no full-page reload. |
| Bottom-card `Create an account` / `Sign in` link | Click | `<Link href="/register">` / `<Link href="/login">`. Next.js client-side navigation; AuthShell stays mounted. |
| Terms checkbox (register only) | Click | Toggles `agree` state. The error `Required` clears immediately on next submit attempt if checked; does NOT clear on click alone (matches the lazy validation contract — errors are only ever set/cleared at submit time, per reference behavior). |
| Bottom-card link cluster | Tab order | Sits below the submit button in source order — last tab stop on the page. |
| Forgot stub `← Back to sign in` link | Click | `<Link href="/login">`. |
| `<AccountMenu>` trigger (Sidebar avatar, logged-in) | Click | Toggles the Radix popover open. ARIA: `aria-haspopup="menu"`, `aria-expanded` toggles automatically (Radix manages). |
| `<AccountMenu>` trigger | Keyboard: Enter / Space | Opens the popover. (Radix default.) |
| `<AccountMenu>` trigger | Keyboard: Esc when popover open | Closes popover, returns focus to trigger. (Radix default.) |
| `<AccountMenu>` Account item | Click | Closes popover; navigates `<Link href="/preferences">`. |
| `<AccountMenu>` Sign out item | Click | Closes popover; calls `signOut()` (clears `recommend-a.session`); calls `router.push('/login')`. **No confirmation dialog** (CONTEXT D-05). |
| `<AccountMenu>` content | Click outside | Closes popover. (Radix default.) |
| `<AccountMenu>` items | Tab order | Account first, Sign out second (source order). Arrow keys do NOT navigate between items in a Popover (that would require a Menu primitive — Phase 4 explicitly chose Popover, not Menu, per CONTEXT D-07). Tab moves focus to next item; Shift+Tab moves back. |

**Accessibility minimums** (verified at Phase 4 PR):
- Every `<Field>` input has a programmatic label association — the visual `<label>` IS a `<label htmlFor={inputId}>` paired with the input's `id`. Generate the id via `useId()` inside `<Field>`.
- Every form has `<form noValidate>` (we run our own validators; HTML5 validation popups would conflict).
- Every form has a top-of-component skip-target relationship: the first `<Field>` receives focus on page mount via `autoFocus` on the email field (login + register).
- The form-level error banner has `role="alert"` and `aria-live="polite"` so screen readers announce the API rejection without stealing focus.
- The `<Field>` show/hide button has `aria-label="Show password"` (when hidden) / `aria-label="Hide password"` (when visible).
- The `<Field>` error/hint message has `aria-live="polite"` (announced after validation) and `id={\`${inputId}-msg\`}`; the input has `aria-describedby={\`${inputId}-msg\`}` and, when error is present, `aria-invalid="true"`.
- The Terms checkbox label is the surrounding `<label>` element wrapping both the checkbox and the text — clicking the text toggles the checkbox natively.
- Every popover trigger has `aria-haspopup="menu"` (Radix sets this when configured); every popover content has `role="menu"` (Phase 4 ships role="menu" via shadcn primitive customization since we are presenting items as a menu, not generic content).
