    ```ts
    "use client";

    /**
     * Phase 12 (FETCH-07) — Reusable error UX hook.
     *
     * Maps an ApiError discriminated union to the project's user-facing UX policy:
     *   - network / server / forbidden  → toast.error(message)
     *   - unauthorized                  → no-op (wrapper already fired onUnauthorized → signOut → RequireAuth redirects to /login)
     *   - validation                    → no-op (caller renders inline form messages from error.fields)
     *
     * Pass the current ApiError (or null) every render; the hook fires its
     * side-effect when the error reference changes.
     *
     * Example:
     *   const [error, setError] = useState<ApiError | null>(null);
     *   useApiErrorUx(error);
     *   // ... in your submit handler: const res = await apiGet(...); if (!res.ok) setError(res.error);
     */

    import { useEffect } from "react";
    import { toast } from "sonner";
    import type { ApiError } from "@/lib/api/client";

    export function useApiErrorUx(error: ApiError | null): void {
      useEffect(() => {
        if (!error) return;
        switch (error.kind) {
          case "network":
          case "server":
          case "forbidden":
            toast.error(error.message);
            return;
          case "unauthorized":
            return; // wrapper already fired onUnauthorized -> AuthContext.signOut -> RequireAuth redirects
          case "validation":
            return; // caller renders inline (toast on validation is wrong: the form needs to highlight specific fields)
          default: {
            const _exhaustive: never = error;
            void _exhaustive;
            return;
          }
        }
      }, [error]);
    }
    ```

    **Critical:**
    - `_exhaustive: never` is load-bearing — if Plan 12-02's `ApiError` ever grows a 6th kind (e.g. `rateLimited` per CONTEXT deferred note), `pnpm tsc --noEmit` will flag this file as the central decision point.
    - Do NOT call `toast.error` for `validation` even though a backend might return a top-level message. Forms must surface field errors inline (DSGN-06 accessibility / UX policy from CONTEXT D-04).
    - Do NOT call `toast.success` anywhere — success UX is per-screen, not in this hook.
    - The hook MUST be safe to call with `null` (no error). Callers will pass their current state which starts at null.
    - File MUST start with `"use client"` (hook = client-only).

| Boundary | Description |
|----------|-------------|
| `ApiError.message` → `toast.error(...)` (Sonner) | The hook passes `error.message` to Sonner. `message` has been sanitized in Plan 12-02. |
| Lambda response → `apiGet<Movie>` parsing | `recommend.real.ts` trusts the wrapper's JSON parse; runtime validation of the `Movie` shape is deferred to Phase 13 (per CONTEXT — Phase 12 uses the mock shape on faith). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01b | Information disclosure | `toast.error(error.message)` in `useApiErrorUx` | mitigate | Hook reads ONLY `error.message` (never `error.cause`, which is the raw `Error` object). Sanitization happened upstream in Plan 12-02's `sanitizeMessage`. Grep gate in Plan 12-04 verifies `error.cause` is never referenced in any UX-facing file. |
| T-12-06b | Information disclosure | `validation` toast suppression | mitigate | Hook deliberately no-ops for `validation` — backend field errors must be rendered inline by the form, never popped as a toast. This is the locked CONTEXT D-04 behavior; the `case "validation": return;` line is the enforcement point. |
| (recommend.real) | Tampering | Unvalidated `Movie` deserialization | accept | Phase 12 uses the mock's `Movie` shape on faith. Phase 13 plan-phase will read `functions/recommend/` and tighten the type (and add a runtime guard if needed). Risk in P12: a malformed response makes the UI render `undefined` fields — acceptable for a demonstrator; not user-facing until Phase 13 ships. |
| T-12-05b | DoS / wrong-environment call | Server-side import of `recommend.real.ts` | accept | The wrapper handles server-side calls cleanly (returns `unauthorized`). The demonstrator function works from server or client; the screen that consumes it (Phase 13) is a client component, so production server calls are not a real risk. |

ASVS Level 1 — all error-UX-relevant items mitigated. No new auth surface introduced in this plan.
